The one thing that makes tests different/ 03

A red test means one of two things.

the code got better

The change was intended

The test is now outdated. It should be updated to match the new, correct behavior.

the code got worse

It's a bug

The test just did its job and caught it. You must not “fix” the test — you fix the code.

To a machine, these look identical — a red test. Telling them apart is the whole game.
Why the naïve version is dangerous/ 04
Auto-editing a test to make it pass
is a rubber stamp for bugs.

If a tool changes a failing test until it goes green, you've built a test that always agrees with the code — so it can never catch a regression. That's worse than no test: it's false confidence.

A test that can't disagree with the code is not a test.
The rule that makes it safe/ 05

Fix the plumbing. Never touch the verdict.

ARRANGEset up data & fixtures→ automate
›
ACTcall the code→ automate
›
ASSERTwhat's correct→ human decides
DocGuard changes how a test calls your code. It never decides what “correct” means — that's the human's job.

A mechanical fix, end to end/ 10

Rename role → userRole. 12 tests, 0 assertions touched.

test_users.py · RED
def test_create_admin():    u = create_user(role="admin")    assert u.is_admin is True# TypeError: unexpected keyword 'role'
test_users.py · DocGuard fix → GREEN
def test_create_admin():    u = create_user(userRole="admin")    assert u.is_admin is True   ← untouched# ✓ passes
Only the call changed. The assertion — the part that says what's correct — is byte-identical.
The guardrail/ 11

What it will never quietly change: the assertion.

a discount changed 10% → 15% … bug, or intended?
def test_total():    t = checkout(price=100)    assert t == 90     # now fails: got 85
  • DocGuard does NOT change 90 → 85
  • Changing an expected value is a decision about correctness
  • It flags: “behavior changed 10%→15% — intended? If yes, I'll update the expected value.”
That's a human's call. The engine escalates it — it never rubber-stamps it.
The gate, sharpened/ 12

The failure type decides the action.

Compile / reference / import errora rename or moved module — mechanical→ AUTO-FIX
Fixture missing a required fieldschema drift — mechanical→ AUTO-FIX
Assertion value mismatchcould be a bug — ambiguous→ HUMAN REVIEW
New behavior, no test at alla coverage gap→ SUGGEST, human writes
Cleaner than the docs gate — because compile + run signals give you a certainty prose never can.
Why this is the efficient way/ 13

Automate up to the boundary of judgment — and stop.

Precision

The map is imports + coverage — empirical, not inferred.

Trust

The verifier is the test runner — an oracle, deterministic and free.

Safety

Mechanics automated, intent human-gated → can't rubber-stamp a regression.

Test maintenance is mostly mechanical churn. This removes exactly that — with more precision and a better checker than docs allow — and structurally refuses to touch the part that requires a human.
